## 实施顺序与代码分工

1. **工程、配置与开发入口。** 将源码打包、版本信息和安装步骤放进仓库。安装器区分初始化与升级，管理独立的 Caddy 站点片段，先验证组合配置。配置增加版本、字段与预算校验、提示词预读和脱敏的生效设置。增加真正的隔离预览，校正原有正式发布参数的帮助信息。文档列出新旧安装的不同步骤。
2. **调度、保留与公网发布。** 把到期判断和清理从每分钟的重活中分开。在上线、新的一天和过期下架时重建，按实际空闲页决定数据库是否值得压缩。保留完整站点的原子切换和到期清理异常处理。为公开文件附加可重复计算的版本；远端模式独立发布、读回版本后放行推送。Caddy 直供路径继续可用，Pages 提供产物部署路径。配置密钥、证据和订阅者不进入公开产物。
3. **新闻发现与编辑质量。** 给每个板块记录目录读取、窗口内线索、原文取得、核验和刊发数量。用可验证时间判断来源覆盖。给跨刊期的相关事件建立可回查的关联，保留一期多事件新闻稿的区分。显示官方陈述、单一媒体报道或独立多源等证据性质。兼容旧稿，沿用现有引文和人工可核查来源。
4. **模型成本与故障隔离。** 提供配置分工和现有模型统筹两种路径；处理服务端繁忙时的退避。收窄修订请求中的稿件范围，让补搜与初次检索共享预算。保留同步双语发行选项，增加中文先发、按篇续译和按订阅要求放行的路径。译文补齐后重建网站，保留原刊身份和已成功投递的状态。
5. **整合。** 从定时任务、手工生成、预览、翻译、构建、清理、推送分别追到落盘和发布入口。重点复查首次启动、旧 SQLite/旧 JSON、空刊、跨日、网络中断、部分翻译成功、同版重复发布和过期队列。订阅者按偏好取件，运维告警独立于新闻的可读状态。

## 发布与观测

先在源码分支完成集成。记录正式版本、配置版本、本地站点版本、公网确认版本。以后部署时先安装确定版本，选择直供或远端发布，确认静态来源地址和推送对象，再启用相应定时任务。既有 Git 站点历史、服务器凭据及订阅策略由部署方决定。

上线后以同样的时间窗口比较每日无变化建站次数、公网发布时间滞后、每篇刊发的已记录 token 数及各板块的候选转化。质量抽查分别统计同期重复、进展误标和来源归属错误，空栏结合来源覆盖判断。按本次要求，交付前采用源码和差异静态检查；实际运行、故障演练与线上效果需在允许执行后验证。
